# 环境发现：`dsh-file-claim` 互斥锁被"活着但空闲"的会话钉死（2026-11-04）

> 归属：本文件是**原区记录**。按[共享知识约定](C:/Users/hello/.agents/治理约定/共享知识.md)，
> 这条属于跨区可复用的工具环境经验，应晋升到 `D:/活/总控/知识库/条目/`；
> 本会话没有 `knowledge_write` 工具，故按约定"先在原区留待同步内容并说明"。

## 现象

同一工作区里有一条并行会话（`session-9f1f58e1…`）通过 `dsh-file-claim` 认领了
`mods/ContinuousScene/state/MEMORY.md` 与 `state/journal.md`，18:42 之后再无任何写操作、
心跳也停了 37+ 分钟，但：

1. `claim_files`（含 `force:true`）均被拒："正被活跃会话占用" —— 判据跟着**进程存活**走，
   不跟心跳走；它的 DSH 进程还活着，所以永远不算 stale。
2. 更坏的是锁文件本身：`<工作区>/.dsh-file-claim.lock` 记录 `{"pid":24028,"at":…}`，
   **即使我不调用任何认领工具，删掉后 200ms 内就被同一 pid 重新创建**；
   于是所有认领操作都卡在"等待会话锁超时"，连**未被认领的文件**都认领不了。

## 判据与处置（本次实测）

- 判断"是不是我自己的锁"：看 `at` 时间戳是否只在**我发起认领时**才刷新。若删掉后无人操作又自动重建，
  说明是**另一个存活进程**在持有。
- 处置顺序：
  1. 先 `who_claims` / `claim_status` 看真实占用与心跳；
  2. `claim_files` → 失败再 `claim_files(force:true)`（心跳 stale 时有效）；
  3. 仍失败且锁文件被自动重建 ⇒ **不要反复删锁**（本次删了 3 次，只是短暂恢复；
     第二次成功认领了一个未被占用的文件，但随后又被钉死）。
     正确做法是**结束那条会话**（关掉它的窗口/会话），锁随之释放；
  4. 期间不要绕过护栏直接改被认领文件（治理要求遵守保护流程）；把待合并内容写进
     **未被认领的新文件**（本次是 `state/bullet-grid-20261104.md`）并提交，让接手者一次粘贴。

## 附带教训

- 确认"对方已释放"不能只听描述：`claim_status` 的心跳、`who_claims` 的占用、
  以及锁文件是否自动重建，三者要一起看。
- 用 PowerShell 读写含中文的 UTF-8 文件会因 GBK 解码把内容写成乱码
  （本次把一份报告整篇写坏过）；这类文件一律走 `read`/`edit`/`write` 工具或 Python 显式 `encoding='utf-8'`。
