**判读**：这批 2048×1123 全屏运行里，长帧的绝大多数就是**内存回收（GC/释放）落在这一帧**；`resident` 在同一帧仍在增长，说明回收的不是地块缓冲，而是别的大块临时内存。上一轮 v14 归因说“29 个长帧只有 9 个邻近 GC（31%）”，与本轮 85–100% 的差别来自**口径**：v14 用插桩 GC 回调，本轮用逐帧 `totalMemory` 回落（同时包含 mark-sweep 与显存/缓冲释放）。两者不矛盾，但**本轮口径更贴近玩家感受到的冻结**。

## 2. 为什么反复回收：分配速率而不是“垃圾小对象”

- 每块新地块在 `sceneBeginWarm` 里分配 4 张 400×400 ARGB = **2.56MB**，实测约 **1.8 块/秒** → **≈18MB/s**；这些缓冲**长期驻留、从不复用**（`Grafon.as:510-534` 无逐出）。
- AIR 的回收由分配量推动，于是约每 **80 帧（2.7 秒）**触发一次 50–165MB 的回收，每次把所在帧拉到 **100–171ms**。
- 这解释了此前四次“减分配≠减帧时”的困惑：被削减的是**小垃圾**（字符串、装箱），而触发回收的是**大地块分配量**。要动的是后者。

## 3. 由此得到的候选（原 P3，现在有了新理由）

**远处逐出 + 缓冲复用**：
1. `sceneDrop` 不再 `dispose()`，把 4 张缓冲压进池（上限 8 块 = 32 张 ≈ 20MB）；
2. `sceneBeginWarm` 优先从池里取（并 `fillRect` 清零），取不到才分配；
3. `sceneTick` 里当 `sceneResident` 超过上限（默认 96 块 ≈ 246MB，可通过 `World.w.visual.root["sceneChunkCap"]` 运行时改）时，逐出**离视口最远**的块。

**预期**：新块分配速率从 18MB/s 降到接近 0 → 回收周期显著变稀 → ≥100ms 帧按比例下降；同时驻留内存被封顶。

**已知风险**（必须先验）：
- 逐出的块若被 CS 呈现层（`SceneEventBitmapFill`，全屏 `scaleV=1` 时总是启用）持有引用，可能出现残影/空洞 —— 必须先核对呈现层对 `sceneSurfaces()` 消失的处理；
- 玩家折返时被逐出的块要重新预热，可能转为同步补画（31–178ms）——需要用本轮探针验证回头路；
- 逐出与 `sceneMarks`/区域的语义耦合。

## 4. 呈现层兼容性（本轮核对，逐出方案的关键前置）

全屏 `scaleV=1` 下 CS 呈现层总是启用（实测 `presented: true`）。核对 `src/SceneEventBitmapFill.as`：

- 第 64-66 行的失效条件里**已经包含 `evictions!=grafon.sceneEvictions`**——即呈现层本来就预期地块会被逐出；
- 第 187-232 行 `refreshBindings()` 每次从 `grafon.sceneSurfaces()` **整体重建**绑定，第 201 行对消失的位图执行 `restoreRecord`（恢复 alpha），随后重建 4 个绘制节点的指令；
- 第 280-281 行的资源记账 `liveRecords==0 && nodesCreated==nodesRemoved` 在 `clear()` 路径上校验。

**结论**：逐出不是“未支持的路径”，而是呈现层设计时已经留了钩子的路径；逐出后绑定会在下一帧刷新。仍需实测确认的是：折返时被逐块重新预热的代价、以及逐出瞬间是否有 1 帧残影。

## 5. 未验证边界

- 本结论只覆盖 2048×1123、正式 13 模组 + 探针、脚本走位/战斗/单天角兽三种夹具；未覆盖真实玩家长时间游玩。
- `totalMemory` 回落不等于“一定是 GC”，也可能是 AIR 释放显存/缓存；但**回落与长帧同帧**这件事本身已被三次运行稳定复现。
- 复算：`python -c` 读 evidence/*/storage/result.json 的 `memoryBytes`/`scene.sceneResident` 差分即可。

## 6. 逐出+复用候选实测：**负结果，不部署**

按 §3 实现的候选（`opt-20261104/cap-diag-v2`：`sceneDrop` 入池 ≤8 块、`sceneBeginWarm` 取池并清零、`sceneTick` 按离视口最远逐出到 `sceneChunkCap=96`），同探索线路 1149 帧对照：

| 指标 | 基线 `phase2-explore-n1` | 候选 `cap2-explore-n1` |
|---|---:|---:|
| 均值 / 中位 / P95 | 41.8 / 38 / 65 ms | **39.9 / 36 / 62 ms** |
| **最大帧** | 171 ms | **568 ms** |
| ≥100ms 帧 | 13 | 11 |
| 同帧内存回落 >1MB | 11 | 10 |
| 驻留块 | 49→**181** | 53→**96（封顶生效）** |
| 逐出次数 | 0 | 0→**79** |
| 内存峰值 | 462MB | **395MB** |
| **同步补画** | 22 次 / 1044ms | **30 次 / 1997ms** |

失败机制（逐帧定位）：
- `dt=568ms` 出现在 **phase 45（相机瞬移 1200px 换窗口）age=0**：该帧 `syncCount` 跳到 25、`warmMs=4514`；
- `dt=431ms` 出现在 phase 49（收尾换窗口）age=0，`syncCount` 到 30；
- 即：**逐出后一旦发生相机跳变（换窗口/传送），缺口只能靠同步补画填**，代价 100–500ms/次，比它省下的 GC 帧更糟。

**判定：不部署。** 该形态把“约每 2.7 秒一次 ~100ms 的回收停顿”换成了“相机跳变时一次 400–570ms 的补画风暴”，尾部明显恶化（P95 略好，但最大帧 171→568ms）。要把这条路走通，需要“缺块异步填充/占位”这类更大的渲染改动，已超出本模组当前范围。

## 7. 结论与建议

- 在全屏 2048×1123 下，**长帧的主因是 AIR 的内存回收**（85–100% 与 50–165MB 回落同帧），其触发源是**永不逐出的地块缓冲分配（≈18MB/s）**；但直接加逐出会把成本转移成同步补画风暴。
- 可接受的折中只有“更保守的上限”（例如 160 块）——按本夹具 `resident` 峰值 181 计算，它只能省下约 12% 的分配量，收益与风险不成比例，暂不做。
- 若要根治，需要“异步补块 + 占位呈现”（把同步补画从主线程移除），这一项应当在有独立验收条件时单独立项。
