# 多敌人活动卡顿调查：每敌人成本与 O(n²) 碰撞归因（2026-11-01）

## 用户报告

"出现多个活动的敌人实体时会产生明显不能归因于镜头移动的卡顿"

## 方法

构建 v12 探针（可变敌数 0/3/12），在当前部署宿主 CA94AF17 上用同一战斗走动路线测量。同时读取 Bullet.as 反编译源码分析碰撞算法。

## 每敌人成本曲线

| 敌人数 | 静止 | 战斗静止 | 战斗走动 | 每敌人增量（战斗走动） |
|---|---:|---:|---:|---:|
| 0 | 33.6 | 33.4 | 36.6 | — |
| 3 | 33.3 | 37.8 | 41.6 | +5.0ms (1.67/enemy) |
| 6（参考） | — | — | 42.5 | +5.9ms (0.98/enemy) |
| 12 | 33.4 | **56.8** | **54.6** | **+18.0ms (1.50/enemy)** |

- 12 敌人时战斗帧 54-57ms，**超出 33ms 目标 24ms**——这就是用户感受到的"明显卡顿"
- **超线性增长**：战斗静止从 1.47/enemy（3敌）增至 1.96/enemy（12敌）
- 非战斗相位（静止/走路）不受敌人数影响

## 根因：O(n²) 子弹碰撞

**Bullet.as 第 503 行**（反编译源码）：
```actionscript
for each(_loc2_ in loc.units)  // 遍历所有 ~130 个单位
{
    if(sost/disabled/trigDis 检查) continue;
    if(X >= _loc2_.X1 && X <= _loc2_.X2 && Y >= _loc2_.Y1 && Y <= _loc2_.Y2)  // AABB
    {
        // 命中处理：dopTest, udar, 音效, 特效, 伤害
    }
}
```

- **每颗子弹**每帧遍历**所有单位**（~130 个）
- **无空间分区**（无网格/四叉树）
- 12 敌人战斗时 ~30-60 发子弹同时飞行
- 总检查数/帧：30-60 × 130 = **3,900-7,800 次 AABB**
- 加上命中处理（音效播放、特效创建、伤害计算），合计约 **1.5-2.0ms/敌人**

叠加因素：
- 命中产生的**音效/特效**增加分配和渲染
- 每个活动敌人的 `animate()` 更频繁（gotoAndStop 链）
- TDFC 模组对更多单位做 AI 快照

## 证据

- v12 探针：`camera-v12-e{0,3,12}-r1`
- Bullet 源码：`game-reference/decompiled/1.02/src102/scripts/fe/weapon/Bullet.as:503`
- 并行会话审查确认物体层渲染 8-10ms 为最大渲染成本

## 优化方向（按可行性排序）

1. **空间分区碰撞**（最大收益，工程量大）：在 Bullet 中用网格索引替代全量遍历，将 O(n) 降为 O(k)（k=网格内单位数）
2. **单位列表预过滤**（中等收益，中等工程量）：sceneTick 构建视口内单位子列表，Bullet 只查子列表
3. **降低子弹频率**（直接但改玩法）：减少敌人武器射速
4. **批量音效/特效**（小收益）：命中处理中减少即时创建

## 结论

多敌人卡顿的**主要来源**是子弹碰撞的 O(n²) 架构，不是镜头移动或地形渲染。当前四层优化已解决了镜头移动侧的问题；剩余卡顿需要**碰撞检测优化**或**敌人密度管理**。
