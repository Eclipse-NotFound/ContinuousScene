# 图集物理尺寸实验

仅供隔离归因，不是生产方案。实际首轮结果见下文。

`atlas_transform.transform(source)` 只接受 SHA256 为
`C0E40368FD8BF6FE1413EC4C8D533C7034B18297AEB35119FBFEC4ADD5D93175`
的冻结 `SceneRasterPresentation.as` 原文，返回修改后的字符串；不读写文件。
输入应为原始 UTF-8 字节直接解码的文本，不先格式化。

唯一变更是在四层分配循环前，用两个局部整数分别计算不小于
`next.width`、`next.height` 的最小 2 的幂，并替换 `BitmapData` 构造器的宽高。
`next`、`bounds`、世界位置、格子筛选、复制矩形与目标坐标、修订号、显示顺序和清理逻辑全部保持。
反向替换必须逐字还原输入。当前原生图块是 400×400；本实验不假定原生尺寸为 2 的幂。

新增区域分配时仍为透明黑（`true, 0`）。格子写入仍依据原逻辑边界。
旧图集继承复制仍使用原代码的 `bitmapData.rect`，因此重建后，透明余量可能被旧图集的内容覆盖；
本转换没有另加裁剪或清空来掩盖这一差异。逻辑边界之外的显示影响仍须由像素结果判断，不能预先声称等价。

内存按实际扩大的尺寸计算：四层像素载荷为 `16 × widthPow2 × heightPow2` 字节。
例如 4096×2048 四层为 128 MiB，不含原生图块、截图、向量、运行时或显卡缓存。
逐层替换时，新旧像素同时存在；若每层旧、新载荷分别为 O、N，理想即时释放下的图集载荷峰值为
`max(4O + N, 4N + O)`，实际进程峰值还会更高。尺寸向上取整可能触及 AIR 位图尺寸或内存限制；
不缩小图像、不降低现有进程内存保护，也不将分配失败解释成像素通过。

## r1实际结果

2026-10-25探针543030DD（冻结收据probe-builds/probe-source/f9a6cee3dc5f4e29a22facf634c6543f/probe-build.json）完成五视口检查与960帧，总31744ms。五视口全部RGB最大差1、alpha0、恢复全0；15/15截图释放，预绘/驻留八计数零变化。实际前两个视口四层4096×4096，占256MiB；另三个四层4096×2048，占128MiB。

移动合并原生均40.604/中37/P9557ms，补尺寸版本35.0875/33/48ms。两对移动均值35.783→34.333、45.425→35.842；第一对P9543→48反而更差，第二对65→46。静止24.979→31.596ms；首建图348ms保留，后静止31ms仍慢，不能全归一次分配。移动期间无重建、无复制，不证明远距离或真实战斗表现。

首轮通过不足以断定尺寸修复了旧RGB2。后续camera-atlas-size-compare-20261025-r1同场同帧在第四视口得到旧/新均RGB2，恢复全0，否定这个修复假设。停止pow2生产推进。正式版本未部署；用户后来接受RGB2的新范围不改变该失败结论，后续回原尺寸避免额外内存和建图成本。
