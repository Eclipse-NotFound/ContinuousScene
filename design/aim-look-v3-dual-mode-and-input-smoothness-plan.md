## 一、 用户实测问题陈述与痛点聚焦

在 0.9.9 版本发布并由玩家实机体验后，反馈了以下三个直接影响操作体验的核心问题：

1. **问题 1（焦点脱离）**：按 `Alt` 键后鼠标会脱离游戏，只有再单击一次鼠标左键，光标才能回到游戏中恢复操作。
2. **问题 2（动力学与空间反馈断层）**：按 `Alt` 后的注视模式镜头移动不够平滑，玩家无法建立“**鼠标越靠近屏幕边缘看的越远**”的直观连续物理反馈。
3. **问题 3（平行模式诉求）**：玩家希望**保留上一版（0.9.8）的按住 Alt 进行注视**，并将其与切换模式作为对等的**平行模式**并存。

## 二、 深度技术调查与根本原因剖析

针对上述三点，我们结合 Win32 消息循环、Adobe AIR / Flash Player 桌面运行时机制、反编译源码以及人机交互控制论进行了深度调查。

---

### 1. 问题 1 调查：按 Alt 导致鼠标脱离游戏（Win32 菜单陷阱与事件透传）

#### 1.1 Win32 消息循环中的 `WM_SYSCOMMAND (SC_KEYMENU)` 机制
- 在 Windows 操作系统体系中，单发 `Alt` 键（虚拟键码 `VK_MENU`，keyCode 18）具有极高的系统特权，被定义为**激活窗口系统菜单/菜单栏的全局快捷键**。
- 当一个 Win32 顶级窗口接收到单纯的 `WM_SYSKEYDOWN` 并随之接收到 `WM_SYSKEYUP`（且期间未按下其他字符键）时，默认的窗口过程函数 `DefWindowProc` 会拦截该消息并向窗口发送 `WM_SYSCOMMAND`，附带参数 `SC_KEYMENU`。
- **后果**：
  1. 窗口立即进入**系统菜单等待/导航状态**（Menu Mode）。
  2. 操作系统会强制解除当前窗口对鼠标的独占捕获（`ReleaseCapture`）。
  3. 窗口停止向内部应用派发连续的鼠标移动与交互事件，直到用户按下 `ESC` 或在窗口客户区内单击一次鼠标左键（产生 `WM_LBUTTONDOWN` 使系统退出菜单模式并将输入焦点重新交还客户区窗口）。
  4. 这与用户描述的“*鼠标脱离游戏，只有再单击一次左键才能回到游戏*”在现象和时序上**100% 吻合**。

#### 1.2 Flash Player / AIR Desktop 键盘事件处理缺陷
- 在 `ContinuousScene` 现有的 `SceneAimController.as`（0.9.8 与 0.9.9）中，按键监听实现如下：
  ```actionscript
  private function onKeyDown(event:KeyboardEvent):void {
      keyDown(event.keyCode, event.ctrlKey, event.altKey, event.shiftKey);
  }
  private function onKeyUp(event:KeyboardEvent):void {
      keyUp(event.keyCode);
  }
  ```
- **核心漏洞**：监听函数中**从未调用 `event.preventDefault()` 或 `event.stopImmediatePropagation()`**！
- 在 Adobe AIR 体系中，如果 AS3 层没有显式调用 `event.preventDefault()`，AIR runtime 会认为当前应用未消费该系统按键，从而将该击键消息原封不动透传给宿主操作系统底层的 Win32 消息泵，直接命中上述的 `SC_KEYMENU` 菜单陷阱。

#### 1.3 原版 Remains 游戏键位设计的启示
- 查阅 `game-reference/decompiled/1.02/src102/scripts/fe/inter/Ctr.as`，原版游戏在全局注册了 44 个操作按键（`keyLeft`, `keyRight`, `keyJump`, `keyRun`, `keyLook` 等）。
- **原版 44 个默认按键中，完全没有使用单独的 Alt 键**！
  - 原版看远探头 `keyLook` 默认绑定为分号键（`;`）；
  - 跑步绑定为 `Shift`；
  - 独角兽念力绑定为 `Q` 或鼠标右键；
  - SATS 绑定为 `V` 或鼠标中键；
  - 武器与法术绑定为数字键与 `Z`, `X`, `C`, `F`, `R` 等。
- **结论**：在 Windows PC 桌面应用中，单独使用裸 `Alt` 键作为高频游戏控制键本就属于高风险设计。我们既要在事件层做好严密拦截，也必须在人机工效层面提供更稳健的键位选择。

### 2. 问题 2 调查：缺乏“越近边缘越远”反馈与移动不够平滑（控制模型失真）

#### 2.1 0.9.9 “边缘硬锚定”的过度设计与体验断层
在 0.9.9 的重构中，为了解决 0.9.8“鼠标移向敌人时镜头缩回”的问题，引入了边缘锚定机制（`steer`）：
1. 设定了 `DEADZONE = 150` 和 `EDGE_BAND = 90`；
2. 鼠标离开中心、在屏幕中间绝大部分区域（约 80% 视野）活动时，`band < 0`，算法直接 `return`，**目标偏移量恒定为 0**；
3. 鼠标推到屏幕边缘 90px 范围内时，强制要求停留整整 3 帧（`EDGE_FRAMES = 3`，约 100ms）；
4. 3 帧满足后，`anchored = true`，目标偏移量突然从 0 跃迁为最大值 `MAX_OFFSET_X = 700`（乘以深度比率）；
5. 锚定后，鼠标在视野内任意位置移动，目标偏移量均不再改变，死锁在远端。

**该机制对玩家体验造成的破坏**：
- **无渐进反馈**：鼠标向外推移的前 350+ 像素内，镜头完全不推；
- **突兀冲击**：一旦满足边缘 3 帧，镜头突然被赋予极大的目标并向外狂奔，玩家感觉“不是自己在推镜头，而是被系统强制拖过去”；
- **无法微调远近**：玩家无法通过准星位置控制“我想稍微看远一点点（例如 200px）”还是“我想看到最远（700px）”；
- **心理模型破裂**：完全违背了用户“**鼠标越靠近屏幕边缘看的越远**”的直觉预期。

#### 2.2 为什么 0.9.8 的“移回视野射击”会导致镜头回缩？（代数环分析）
我们要弄清楚 0.9.8 的病根在哪里，才能在恢复连续距离反馈的同时避免历史倒退：
- 摄像机平移与屏幕坐标的代数关系为：
  $$\text{camOffset} = g(\text{cursorScreen})$$
  $$\text{targetWorld} = (\text{targetScreen} - \text{camPos}) / \text{scale}$$
- 当玩家在屏幕边缘把镜头推出去 700px 后，远处的敌人被拉入屏幕（例如出现在屏幕右侧 $x = 700$ 处）。
- 玩家为了射击敌人，必须把准星移向敌人的屏幕坐标（从 $x = 950$ 移到 $x = 700$）。
- 在 0.9.8 中，由于镜头偏移与鼠标到中心距离是完全刚性的对称线性关系：鼠标移回 $x=700$，到中心的距离骤减，镜头偏移量立刻从 700px 缩水到 350px。
- 镜头向左缩回 350px，导致敌人重新被甩出屏幕右侧（$700 + 350 = 1050$）。
- **这就是代数环振荡（Algebraic Loop Oscillation）**：鼠标追敌人导致镜头缩回，镜头缩回导致敌人出屏。

#### 2.3 正确的数学解法：连续非线性距离映射 + 不对称动力学保持（Asymmetric Soft Retention）
解决上述矛盾，不需要粗暴地用“开关式边缘锁”替代距离反馈，而应当采用现代游戏摄像机经典的**不对称响应控制律**：
1. **连续距离前向推进（Forward Push）**：
   - 目标偏移量的大小由鼠标离屏幕中心的实际距离直接决定，满足：
     $$T = \text{normalize}(\mathbf{D}) \cdot R_{\max} \cdot f\left(\frac{|\mathbf{D}| - r_{\text{dead}}}{R_{\text{screen}} - r_{\text{dead}}}\right)$$
   - 其中 $f(u)$ 是平滑非线性函数（例如 $u^{1.3}$ 或 Smoothstep），确保在中心附近平缓，随着鼠标靠近屏幕边缘平滑、单调增大至 100%。
   - 这恢复了“**鼠标越靠近屏幕边缘看的越远**”的纯正物理操作感。
2. **射击微调保持（Aim Engage & Soft Retention）**：
   - 为什么人在瞄准射击时镜头不能乱动？因为人在射击时注意力在目标敌人上，准星在敌人身上做微小的微调瞄准（Flick & Tracking）。
   - **解耦方法：速度与方向的不对称阻尼（Asymmetric Damper）**：
     - 当鼠标向外推（距离增大）时，动力学平滑时间较短（$T_{\text{in}} \approx 0.25\text{s}$），**响应极其敏捷、指哪打哪**；
     - 当鼠标在远端同一朝向半球内微调（准星回移瞄准敌人）时，系统进入**软滞后保持区（Soft Retention / Hysteresis Hold）**：
       回缩平滑时间大幅增加（例如增大至 $0.8\text{s} \sim 1.2\text{s}$，或者在同朝向下维持当前的视野延展峰值），镜头**保持在当前延展位置，不会剧烈缩回**，从而允许玩家从容移动准星瞄准射击；
     - 当玩家**明确拉回鼠标至中心死区（或松开按键）**时，系统立即确认“退出注视”，镜头迅速平顺归位（$T_{\text{out}} \approx 0.20\text{s}$）。

### 3. 问题 3 调查：长按模式（Hold）与切换模式（Toggle）的平行共存

#### 3.1 两种模式的战术差异与玩家分流
- **长按注视模式（Hold to Peek，0.9.8 传承）**：
  - **核心体验**：按住按键立即看远，松开按键即刻回弹回角色。
  - **适用场景**：中短距离遭遇战、掩体探头、突发索敌、狙击前瞬间确认。
  - **心智模型**：高度安全。遇到险情只需松手，镜头瞬间回到自身，绝不会因“忘记再按一次退出”导致被贴脸近战击杀。
- **切换注视模式（Toggle to Look，0.9.9 演进）**：
  - **核心体验**：按一次进入注视状态，再按一次退出。
  - **适用场景**：大地图开阔地长途行军、据点外部定点狙击、巡视巡逻。
  - **心智模型**：解放左手。左手无需持续死按按键，可自由操控 WASD、跳跃（Space）、换弹（R）。
- **结论**：这两者不存在“孰优孰劣”，而是两种截然不同的战术操作风格。0.9.9 强行用 Toggle 覆盖 Hold 是错误的，必须将二者构建为**平等的平行模式（Parallel Modes）**。

## 四、 详细设计与实现细节

### 1. 根治 Alt 导致鼠标脱离游戏（输入层重构）

#### 1.1 完整的事件拦截（Prevent Default）
在 `SceneAimController.as` 中，改写 stage 键盘事件处理：
```actionscript
private function onKeyDown(event:KeyboardEvent):void {
    if (isTriggerKey(event.keyCode, event.ctrlKey, event.altKey, event.shiftKey)) {
        // 关键点：显式调用 preventDefault，阻止 Win32 消息泵接收 SC_KEYMENU
        event.preventDefault();
        event.stopImmediatePropagation();
    }
    keyDown(event.keyCode, event.ctrlKey, event.altKey, event.shiftKey);
}

private function onKeyUp(event:KeyboardEvent):void {
    if (isTriggerKey(event.keyCode, event.ctrlKey, event.altKey, event.shiftKey)) {
        event.preventDefault();
        event.stopImmediatePropagation();
    }
    keyUp(event.keyCode);
}

private function isTriggerKey(keyCode:int, ctrlKey:Boolean, altKey:Boolean, shiftKey:Boolean):Boolean {
    if (triggerModifier == 0 && (keyCode == 18 || altKey)) return true;
    if (triggerModifier == 1 && (keyCode == 17 || ctrlKey)) return true;
    if (bindingMatches(keyCode, ctrlKey, altKey, shiftKey)) return true;
    return false;
}
```

#### 1.2 提供更稳定安全的按键推荐（左 Ctrl）
- 虽然 `preventDefault()` 可以阻止绝大部分 AIR 窗口的菜单激活，但部分 Windows 环境在窗口失焦重获时可能仍会对 `Alt` 产生边缘残留。
- 在设置界面中明确提示：
  - `0 = 左 Alt`（已加防脱离拦截保护）；
  - `1 = 左 Ctrl`（**强烈推荐**：Windows 零系统菜单副作用，原版 Remains 完全无键位冲突，极度顺手）；
  - `2 = 停用内建键`（仅使用用户自定义单键/组合键）。

#### 1.3 窗口失焦保护与光标自动恢复
- 监听 `Event.DEACTIVATE`：当玩家 Alt+Tab 或窗口意外失去焦点时，立即执行 `deactivate()` 清空所有按键状态，并调用 `restoreCursor(cam)` 恢复坐标基准，防止因卡键导致镜头漂移。

### 2. 连续平滑距离反馈与瞄准保持（动力学与控制层重构）

#### 2.1 连续非线性距离映射曲线
废除 0.9.9 的“非边缘即 0”的二值切分，构建连续的空间响应曲线：
1. **死区与有效域**：
   - 屏幕中心死区半径调优为 `DEADZONE = 70` 像素（给角色近战和近身瞄准留足静止空间）；
   - 最大有效半径取屏幕半宽与半高的对角线比例（约 450~550 像素）。
2. **归一化距离映射**：
   - 计算鼠标偏离中心向量 $\mathbf{D} = (dx, dy)$，距离 $d = \sqrt{dx^2 + dy^2}$；
   - 若 $d \le \text{DEADZONE}$，则归一化输入 $u = 0$；
   - 若 $d > \text{DEADZONE}$，则计算：
     $$u = \text{clamp}\left(\frac{d - \text{DEADZONE}}{\text{MAX\_DIST} - \text{DEADZONE}}, 0, 1\right)$$
   - 应用平滑非线性过渡函数（Smoothstep 或缓入幂律）：
     $$S(u) = u^{1.25} \quad \text{或} \quad S(u) = u^2 (3 - 2u)$$
     这种曲线保证了在死区边缘起步极为轻柔，随后随鼠标推远平滑加速展开，推到屏幕边缘时达到满额 $1.0$。
3. **目标偏移向量计算**：
   $$T_x = \frac{dx}{d} \cdot \text{MAX\_OFFSET\_X} \cdot \text{distanceScale} \cdot S(u)$$
   $$T_y = \frac{dy}{d} \cdot \text{MAX\_OFFSET\_Y} \cdot \text{distanceScale} \cdot S(u)$$
   这样，玩家将鼠标向右推 30%，镜头就平滑向右延伸 30%；推到最右侧边缘，镜头延伸至最远端；鼠标稍微拉回，镜头立刻呈现出柔和的距离回缩响应！

#### 2.2 瞄准射击时的“视线保持 / 软滞后”（Soft Retention）
为了彻底解决“准星移向敌人瞄准射击时镜头抖动回缩”的问题，我们设计了**方向保持与回缩阻尼机制**：
- **概念**：
  当玩家在瞄准模式下将视角推向某一方向（例如右方，角度 $\theta$），算法记录当前达到的**视线延伸深度（Peak Reach）**。
- **判断准星是在“微调瞄准”还是“主动放弃注视”**：
  - **微调瞄准（Engage）**：准星依然位于推进方向的同一象限/半球（$\mathbf{D} \cdot \mathbf{LookDir} > 0$），且未掉入中心死区；
  - 此时，即使准星因为瞄准敌人而从边缘移回屏幕内部，目标偏移量的衰退速度被施加高阻尼缓冲（$T_{\text{settle}} = 0.8\text{s}$），或者目标偏移量保持在 $\max(S(u), 0.75 \times \text{PeakReach})$；
  - 这样，准星在敌人周围移动瞄准时，镜头如同拥有“磁性锁定”一般平稳支撑视野，绝不会发生剧烈闪回；
  - **主动收回（Retract）**：一旦鼠标明确拉回中心死区（$d \le \text{DEADZONE}$），系统判定玩家意图归位，立即解除保持，镜头以 $T_{\text{out}} = 0.20\text{s}$ 顺滑回正。

> **实施时修正**：这一条“拉回中心死区收回”在手感上不成立——视野延展后屏幕中心恰是新露出地面的中部，
> 瞄准那里会掉视野（0.9.8 的代数环换个位置复现）。落地版本改为：**收回只由触发键决定**（长按松开 / 切换再点），
> 保持也不是高阻尼而是“只许向外抬升 + 3 帧跟随”，方向仅在准星处于边缘环带内才允许缓转。
> 详见 §八 差异表与实际代码。

#### 2.3 临界阻尼平滑模型（SmoothDamp）
继承 0.9.9 的二阶连续性算法：
- 严格杜绝一阶 lerp 的首帧初速度阶跃；
- 推进（Aim In）时间设为 $0.24\text{s}$；
- 回中（Aim Out）时间设为 $0.20\text{s}$；
- 最大速度设为 1200 px/s，全程无硬切角。
